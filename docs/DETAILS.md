# monad-pure-interp: detailed notes

Goal: a Lean 4 proof that the RISC-V machine code of the monad EVM interpreter,
restricted to pure contracts, agrees with a Lean EVM specification on status,
remaining gas and output.

Status: for six opcodes (STOP, ADD, SUB, POP, PUSH1, RETURN) the handler loop
of the real image is proved to compute what EVMYulLean's `EVM.X` computes
(`Top.loop_correct`). The entry and exit of `monad_pure_execute` are proved
only in part, so there is no end-to-end theorem; the intended one is stated
as `Top.PureExecuteCorrect`. See "Not done".

## The binary

`./build.sh` compiles the unmodified monad interpreter sources
(`category/vm/interpreter`, `category/vm/runtime`) for one revision, Cancun,
into a closed freestanding RV64IM ELF, `build/pure.elf`.

- `cxx/pure_interp.cpp` adds the instruction table, a host and the entry point
  `monad_pure_execute(input*, output*)`. Opcodes that touch world state, the
  block or transaction environment, logs or other contracts are mapped to the
  interpreter's `invalid` handler: BALANCE, ORIGIN, GASPRICE, EXTCODE\*,
  BLOCKHASH, COINBASE, TIMESTAMP, NUMBER, PREVRANDAO, GASLIMIT, CHAINID,
  SELFBALANCE, BASEFEE, BLOBHASH, BLOBBASEFEE, SLOAD, SSTORE, LOG0–4, CREATE,
  CREATE2, CALL, CALLCODE, DELEGATECALL, STATICCALL, SELFDESTRUCT, and for now
  KECCAK256, TLOAD and TSTORE.
- `cxx/platform.cpp` supplies a bump allocator, byte-loop `mem*`, shift-subtract
  128-bit division. Only `setjmp`/`longjmp` come
  from the toolchain's newlib.
- `tools/lower_w.py` rewrites the word instructions riscv-zkvm does not
  model (ADDW, SUBW, MULW, SLLIW, SRLIW, SRAIW) into 64-bit instructions plus
  ADDIW. It runs on GCC's assembly output and is not trusted, because the proof
  is about the linked binary.
- Layout (`cxx/link.ld`): code at `0x80000000`, data and a 64 MiB heap at
  `0xa0000000`, matching the memory map the riscv-zkvm model assumes.

Result: 181 functions, 11,117 instructions. Every
instruction is one riscv-zkvm models.

## The Lean side

- `PureInterp/Image/` (generated by `harness/GenImage.lean`): per function, its
  address, raw words, decoded instruction list, and a kernel-checked theorem
  that the words decode to that list. Axioms: `propext`, `Quot.sound`.
- `harness/PureAbi.lean`: the fixed addresses for input, output, EVM stack, EVM
  memory, bytecode and calldata.
- `harness/RunPure.lean`: runs the ELF in the proof model's `step` function.

```bash
./build.sh
(cd harness && nix shell nixpkgs#elan -c lake build)
harness/.lake/build/bin/gen-image build/pure.elf build/symbols.txt PureInterp/Image
nix shell nixpkgs#elan -c lake build
harness/.lake/build/bin/run-pure build/pure.elf 600260030160005260206000f3 "" 100000
# status=success gas_left=99976 output=0x00…05 steps=4302
```

## Handler proofs so far

All over the functions in the binary, standard axioms only
(`Test/AxiomsTop.lean`):

| Theorem | Function(s) | Instructions | What it says |
|---|---|---|---|
| `add_spec` | `f_add` | 44 | With ≥3 gas and two operands: limb-wise sum into the second slot, pop, jump to the table entry for the next opcode byte. |
| `pop_spec` | `f_pop` | 17 | With ≥2 gas and one operand: pop and dispatch. |
| `push1_spec_same`, `push1_spec_split` | `f_push_1` | 24 | With ≥3 gas and stack room: push the immediate byte and dispatch. Two variants, for the immediate and next opcode sharing a doubleword or not. |
| `jumpdest_spec` | `f_jumpdest` | 10 | With ≥1 gas: charge and dispatch. |
| `jumpdest_oog_exit` | `f_jumpdest`, `f_rt_Context_exit`, `f_longjmp` | 30 | With no gas: status 3 stored in the context and control back at the `setjmp` return site. |
| `swap1_spec` | `f_swap_1` | 33 | With ≥3 gas and two operands: exchange the top two words and dispatch. |
| `stop_exit_spec` | `f_stop`, `f_rt_Context_exit`, `f_longjmp` | 29 | From STOP's entry to the `setjmp` return site: gas and status 0 stored in the context, callee-saved registers and `sp` restored from the jump buffer, `a0 = 1`. |

`PureInterp/U256.lean` shows ADD's limbs are the 256-bit sum (via `bv_decide`,
which adds a native-evaluation axiom for its SAT certificate check). The
out-of-gas and stack-check exits of ADD, POP and PUSH1 are not proved yet.

Cross-function proofs (`stop_exit_spec`) are stated over an arbitrary code
requirement `cr` with one inclusion hypothesis per function and one equation
per call target; the whole-image code requirement will discharge them.

How handler proofs are structured:

1. Straight-line blocks are stated generically in their base address and in
   every immediate, and proved by `runBlock` alone.
2. The handler theorem is stated over the concrete function with each memory
   address named by a variable plus an equation, so the tactic never compares
   two literal offsets.
3. Blocks are instantiated, lifted to the function's code with
   `CodeReq.ofProg_mono_sub`, and composed with `runBlock h0 h1 …`. Branches
   become triples with `cpsBranchWithin_ntakenStripPure2`.

Library behaviour to know (riscv-zkvm v0.4.0):

- Two concrete negative `signExtend12` offsets from one base register make
  `runBlock` hit the recursion limit; use symbolic offsets or named addresses.
- A literal base address does the same; keep `base` symbolic.
- `LBU` needs its spec passed explicitly, as its own step.
- Memory is doubleword-granular, so a handler that reads several bytecode bytes
  needs one statement per way those bytes fall into doublewords.
- Shift results keep the form `v <<< (0x03#6).toNat`.
- v0.3.1 mis-selects specs for aliased operands; v0.4.0 (Lean 4.33.1) is required.

## Specification side

EVMYulLean (Cancun) is vendored at `spec/EVMYulLean`, branch `lean-4.33`,
ported from Lean 4.22 to 4.33.1 with no definition changed and no `sorry`
(changes are uncommitted in that clone). It is a path dependency.

- `PureInterp/Spec/Step.lean`: `X_add`, one iteration of the Yellow Paper loop
  `EVM.X` on ADD with enough gas and two operands. The recipe (unfold `X`,
  rewrite the cost and arity facts, use a `rfl` lemma for `EVM.step` on that
  opcode) is about 40 lines and should repeat for other simple opcodes.
- `PureInterp/Refine/Word.lean`: `u256_add` (machine 256-bit addition is the
  spec's ADD) and `gas_charge` (the handlers' `addi a4, a4, -c; bltz` is the
  spec's gas check and subtraction, for counters below 2^63).

Known obstacles in the spec, from the port:

- `ffi.ByteArray.zeroes` and `ffi.keccak256` are `opaque` externs. The first
  sits under every memory read and write, so MLOAD/MSTORE/RETURN cannot be
  reasoned about until it is replaced by a Lean definition or axiomatised.
- `D_J` (jump destination analysis) is `partial`; proofs must target `X`, which
  takes the valid jump set as a parameter, and relate it to the binary's
  jumpdest bitmap separately.
- TLOAD/TSTORE act on the account at `codeOwner`; a pure setup still needs
  that account to exist.

## Intermediate model

`PureInterp/Model.lean` is a small executable definition of what the binary
computes (stack, gas, pc; STOP, ADD, POP, PUSH1 so far). The binary is to be
proved against the model and the model against `EVM.X`; `Model.AgreesWithSpec`
states the second half and is not yet proved.

## The simulation loop (STOP, ADD, SUB, POP, PUSH1, RETURN)

Everything under `PureInterp/Machine/` (`CHANGES.md` there lists what SUB and
RETURN changed in its interface):

- `Words.lean`, `Invariant.lean`, `Lemmas.lean`: arrays of doublewords, the
  invariant `interp L scr limbs depth gas pc` for the machine at a handler
  entry, `Rep limbs stack`, and the lemmas that take a bytecode byte, a table
  entry or stack slots out of the invariant.
- `AddStep.lean`, `SubStep.lean`, `PopStep.lean`, `Push1Region.lean`, `Push1Step.lean`: each
  handler from the invariant for a model state to the invariant for the state
  `Model.step` gives, ending at the table entry of the next opcode.
- `Exit.lean`, `Full.lean`, `Fail.lean`: `exit_chain` (from `Context::exit` to
  the `setjmp` return site), the context and jump buffer (`exitFrame`), the
  final assertion (`final`), and the halting paths: STOP, the invalid
  handler, and out-of-gas and stack errors for ADD, SUB, POP and PUSH1.
- `ReturnFinal.lean`: RETURN (`return_final`, `return_err_final`), over
  `Handlers/Return.lean` and `Handlers/Memmove.lean` (the backward byte loop
  of `memmove`, by induction on the length). The handler charges no gas: it
  copies the offset and size words into the context, stores the gas and
  exits. `ResultOK` ties those context fields to `Model.returnResult`, the
  model of the expansion charge and output that `Context::copy_result_data`
  makes afterwards; proving that function is part of the exit glue.
- `Linked.lean`: `Linked`, the facts `run_sim` needs about the loaded image
  (where the functions are, the table entries, the call offsets) and about
  the run-time layout (the padded bytecode buffer, the stack and context),
  the run restriction `RunOK`, and `ResultOK`. `Top.linked_image` proves the
  image part.
- `Loop.lean`: **`run_sim`**. If `Model.run code fuel s = some r` and every
  executed opcode is STOP, ADD, SUB, POP, PUSH1, RETURN or has the invalid
  handler as its table entry, then from the invariant for `s` the machine
  reaches the `setjmp` return site within `464 * fuel` instructions with the
  context satisfying `ResultOK r`.

`PureInterp/Spec/Agree.lean` proves the other half, `Spec.agrees`: such a run
of the model gives the result EVMYulLean's `EVM.X` gives. For RETURN
(`Spec/Return.lean`) it assumes memory holds only zeros and the gas cannot pay
for `2^23` words of memory, below which the binary's 28-bit offset bound and
running out of gas coincide.

Axioms of `run_sim`: the standard three plus `bv_decide`'s for the three limb
lemmas. `Spec.agrees`: the standard three.

Things to know when extending:

- A new assertion used as a frame needs an `Assertion.PCFree` instance;
  without it `runBlock` leaves a hole and Lean reports "don't know how to
  synthesize placeholder" on every line of the proof.
- Step bounds are checked with `omega`; a wrong bound shows as "No usable
  constraints found".
- `Model.AgreesWithSpec` as first written is false (`Spec.not_agreesWithSpec`):
  the model fails on opcodes it lacks while the spec runs them.

## The real image, and the combined theorem (`PureInterp/Top/`)

- `PureInterp/Image/Link*.lean`: `imageCode` (the whole text segment as one
  code requirement), `f_x.included` for every function, the instruction table
  read out of the data segment (`imageTable`, `imageTable_0xNN`,
  `imageTable_aligned`, `imageTable_invalid_iff`), `link_eq` for pc-relative
  equations, and `ImageLoaded s` for machine states.
- `Top/Linked.lean`: `Dyn L E code` holds the run-time layout facts of
  `Linked` (stack, context and bytecode buffer addresses, alignment,
  accessibility, padding) and the four equations fixing the table and exit
  addresses to the image's. **`linked_image : Dyn L E code → Linked
  Image.imageCode L E code Image.f_stop.addr …`** discharges every static
  field: no fact about the ELF is assumed any more.
- `Top/Loop.lean`: **`loop_correct`**. Under `Dyn`, for a model run that halts
  with `r` and satisfies `Spec.RunSupported`: the machine triple from
  `interp … (30 + s.pc) ** exitFrame …` at the image's handler for the
  current opcode to `final …` with `ResultOK r`, over `Image.imageCode`; and
  `Model.ResultMatches r (EVM.X (fuel + 1) vj e)` for every matching
  EVMYulLean state. `loop_correct_machine` is the same for a machine state
  `m` with `Image.ImageLoaded m`, in terms of `stepN` and `holdsFor`, and
  reads the status and gas out of the context.
  The single run restriction is `Spec.RunSupported`: each executed opcode is
  STOP, ADD, SUB, POP, PUSH1, RETURN, or one of the 108 bytes EVMYulLean
  decodes to `INVALID`. `runOK_of_runSupported` derives the machine side's
  `RunOK` from it (all 108 dispatch to the `invalid` handler; the binary
  sends 34 further, real instructions there, on which model and EVMYulLean
  differ).
- `Top/Statement.lean`: **`PureExecuteCorrect`, a definition, not a
  theorem**: the intended end-to-end claim about `monad_pure_execute` on
  machine states, with the input and output structs, the memory regions that
  must be owned or zero, and the side conditions. Its module comment lists
  what is proved towards it and what is missing.

The bytecode buffer is the one `Intercode::pad` builds: `Linked.padded` is
`L.code = replicate 30 0 ++ code ++ replicate pad 0` with `33 ≤ pad`, and the
invariant for model pc `p` is `interp … (30 + p)`.

`PureInterp/Entry/` has the entry and exit glue proved so far, as separate
pieces not yet joined to the loop: the allocator, `memset`, `memcpy`,
`pad_spec`, `ctor_spec` (conditional on a hypothesis that is the contract of
`find_jumpdests`), `setjmp_spec`, `trampoline_*`, `core_loop_spec`,
`launch_region`, `copy_to_result_error`/`_oog`, `fail_tail_error`/`_oog`,
`out_success`.

Axioms (`Test/AxiomsTop.lean`): `linked_image` and `Spec.agrees` use the
standard three; `run_sim`, `loop_correct` and `loop_correct_machine` add
`bv_decide`'s for the limb lemmas of ADD, SUB and PUSH1.

## Not done

There is no end-to-end theorem. `PureExecuteCorrect` is unproved; the loop
theorem starts at a handler entry with the invariant assumed and stops at the
`setjmp` return site. Missing, in the order of `Top/Statement.lean`:

- `find_jumpdests` (`ctor_spec` assumes its contract), `Context::from`.
- The first 44 instructions of `monad_pure_execute` joined into one triple,
  and its last 40 (cleanup and return).
- `copy_to_result`'s success path and `Context::copy_result_data`. RETURN's
  memory-expansion charge and its output are computed there, so
  `Model.returnResult` is not yet tied to machine code; neither is the
  success path of STOP beyond the context fields. The output buffer comes
  from `calloc`, which relies on unused heap being zero.
- The layer from `launch_region`'s postcondition to `interp ** exitFrame`
  with a layout satisfying `Dyn`, and from `final` to `trampoline_exit` and
  the tails; and instantiating the Entry theorems with `Image.imageCode`.
- Forward `memmove`: the loop needs the operand stack below the context
  (`Dyn.below`).
- The converse of `Spec.agrees` (an `EVM.X` run that does not run out of fuel
  makes the model halt), so the run restriction still mentions the model.
- Three constants in `PureExecuteCorrect` are estimates: the machine stack
  size, the entry/exit part of the step bound, and the gas bound that keeps
  allocations inside the heap.
- All other opcodes.
- The gaps inherited from riscv-zkvm: its decoder is not tied to Sail's, and
  the Sail transfer needs per-step side conditions.
